## 0. 一页理解项目

### 0.1 项目解决的问题

NLSpotify 是一个使用 Objective-C/UIKit 编写的仿 Spotify 风格音乐 App，通过网易云音乐 API 代理获取推荐、歌单、搜索、广播、电台节目、歌曲和评论内容。它把一个“用户点击歌曲”的动作拆成多条需要协同的链路：

1. **内容链路**：首页、搜索、广播、歌单和艺人详情把服务端数据转换成可播放的 `NLSong` 或播放意图。
2. **播放链路**：`NLPlayerManager` 统一管理当前歌曲、播放列表、`AVPlayerItem`、播放状态和系统媒体控制。
3. **字节链路**：`AVAssetResourceLoader` 把 AVPlayer 的 Range 请求映射到内存缓存、磁盘 Range 缓存和 HTTP Range 回源。
4. **资产链路**：用户主动下载走独立的 background `NSURLSessionDownloadTask` 和 `NLOfflineAudioStore`，不把普通播放缓存当成离线资产。
5. **一致性链路**：ReactiveObjC、token、generation、串行写队列、WCDB 事务和启动对账共同处理异步回调、文件和数据库之间的不一致。

项目的核心不是“页面很多”，而是要让下面这个不变量成立：

> **旧异步结果可以迟到，但不能污染当前歌曲、当前搜索、当前下载任务或当前持久化状态。**

### 0.3 三个最重要的工程不变量

| 不变量 | 代码控制手段 | 失败时的结果 |
| --- | --- | --- |
| 旧回调不能更新新对象 | 播放 URL、缓存进度、周期进度、item/player KVO 与重置定位回调使用 `playSwitchToken`，并核对相应 player/item 身份；结束通知核对当前 item；音频会话异步结果使用独立 generation；搜索、下载、歌词各自保留原有过期检查 | 丢弃旧结果，不回滚当前状态 |
| 用户下载资产不能被普通缓存淘汰 | `NLOfflineAudioStore` 独立目录和元数据；`NLCacheManager` 只管理普通 Range 缓存 | 普通 LRU 不删除离线正文；显式删除由下载管理器负责 |
| `completed` 必须对应真实正文和数据库记录 | 系统临时文件导入、离线元数据写入、WCDB 事务按顺序提交 | 任一步失败都不能伪造完成状态 |

### 0.4 当前范围边界

- 当前源码已经接通：推荐首页、歌单/专辑浏览、搜索歌曲/歌单/艺人/歌词查询、艺人热门歌曲、电台推荐/热门兜底/节目列表、在线播放、Range 缓存、行级歌词、只读评论分页、本地歌单/收藏、播放历史、后台显式下载和离线文件播放。

## 1. 先看全链路：从启动到可播放字节

```text
启动
  → 初始化 WCDB / 下载管理器 / 缓存管理器
  → Keychain 迁移并派生登录态
  → 登录页或 TabBar
  → 内容 Service 请求
  → 页面把数据转换成 NLSong / 播放列表
  → NLPlayerManager 产生当前播放上下文
  → 离线正文，否则完整普通缓存，否则已有播放 URL，否则获取播放 URL
  → AVPlayerItem
  → ResourceLoader 按 Range 提供数据
  → ReactiveObjC 把状态交给 UI
  → 播放历史、下载、歌单和缓存账本落入 WCDB/文件
```

每一段只负责一类问题：

- **App 层**负责生命周期、根路由和系统后台 session 事件，不负责解析歌曲或创建 `AVPlayerItem`。
- **Service/网络层**负责 HTTP 请求、Cookie 注入、301/401 刷新和响应解析，不负责决定页面如何展示。
- **页面层**负责内容选择、分页和播放意图，不直接处理音频 Range。
- **播放器层**负责当前歌曲和 AVFoundation 生命周期，不让首页、搜索页各自创建播放器。
- **缓存层**负责字节区间和普通缓存文件，不把普通缓存完成等同于用户下载完成。
- **Repository/WCDB 层**负责本地实体、关系和事务，不让 UI 直接拼接数据库写入。

这种分层的直接收益是：内容入口可以继续增加，但它们只需要产生相同格式的播放意图；播放、缓存、下载和状态传播不需要复制多套实现。

## 2. 链路一：启动、认证与根路由

### 2.1 入口与调用关系

关键文件：

- `NLSpotify/App/AppDelegate.m`
- `NLSpotify/App/SceneDelegate.m`
- `NLSpotify/Networking/网易云API/Login && 双Token/NLAuthManager.m`
- `NLSpotify/Networking/网易云API/Login && 双Token/NLKeychainCredentialStore.m`
- `NLSpotify/Modules/WCDB/NLDataBaseManager.mm`
- `NLSpotify/Modules/播放器/NLDownloadManager.m`
- `NLSpotify/Modules/播放器/缓存/NLCacheManager.mm`

启动分成两条并行方向：

```text
AppDelegate.didFinishLaunching
  ├─ 触发 NLDataBaseManager 单例
  ├─ 创建 NLDownloadManager，重建 background session 任务
  ├─ 创建 NLCacheManager；启动只做目录对账，不按容量淘汰
  ├─ 读取 currentCookie 打启动日志
  │    └─ Keychain 为空、legacy Cookie 存在且读取无错误时，这里就会迁移
  └─ 返回后才进入 Scene

SceneDelegate.willConnectToSession
  ├─ 注册 NLForceLogoutNotification
  ├─ 再次调用 migrateLegacyCookieIfNeeded:（幂等）
  ├─ NLAuthManager.isLoggedIn
  └─ 登录页 / NLTabBarController
```

`AppDelegate` 的 manager 创建不是“所有恢复工作完成后才显示 UI”。数据库、缓存目录对账和下载任务恢复都可能在后台继续。不要把 `currentCookie` 当成无副作用的日志读取。

### 2.2 认证状态流

`NLAuthManager` 使用 Keychain account `NLNeteaseCookie` 保存 Cookie。登录态不是独立可信的 `NSUserDefaults` 布尔值，而是由当前能读到的非空 Cookie 派生：

```text
currentCookie 非空
        → isLoggedIn == YES
        → TabBar

currentCookie 为空
        → 登录页

currentCookie 读取顺序：
  1. Keychain account NLNeteaseCookie 非空：直接返回，不依赖旧布尔标记
  2. Keychain 为空或读取失败：回退旧 NSUserDefaults Cookie
  3. 只有 Keychain 读取没有错误时，才尝试把旧值写入 Keychain；写入成功后删除旧值
  4. 迁移写入失败仍返回旧值，所以不能把“Keychain 当前为空”说成未登录
```

迁移的关键顺序：

1. Keychain 已有非空 Cookie：清理旧 `NSUserDefaults` Cookie 和旧登录标记。
2. Keychain 读取失败：不删除旧值，并返回迁移失败；旧值仍可作为临时读取结果，避免一次 Keychain 故障造成误登出。
3. 只有旧 Cookie 存在且 Keychain 写入成功：才删除旧 Cookie 和旧登录标记。
4. Cookie 为空时登出：先删 Keychain。只有 Keychain 删除成功，才继续删旧 Cookie、旧登录标记和账户对象。Keychain 删除失败会直接返回，legacy 凭据可能仍在；`logout` 目前忽略这个失败结果。

这里的“登录”是游客 Cookie 登录链路，不是 OAuth2 Bearer Token 体系。真实账号、OAuth 和服务端长期会话有效性仍由网络层的 301/401 处理。

### 2.3 认证失效与根路由切换

`NetWorkManager` 对 GET/POST 都执行相同的恢复策略：

```text
HTTP 401 或业务码 301
  → retryCount 是否已达到 1？
       ├─ 是：失败回调 + 强制登出
       └─ 否：进入 refreshLockQueue
              ├─ 第一个请求成为刷新请求
              ├─ 后续请求进入 pendingRequests
              ├─ 刷新成功：所有请求各重放一次
              └─ 刷新失败：所有请求失败 + NLForceLogoutNotification
```

对于普通业务请求恢复器能够收到 refresh failure 的路径，以及重放后再次遇到 301/401、`retryCount` 达到 1 的路径，`SceneDelegate` 会接到 `NLForceLogoutNotification`，用 0.5 秒 `kCATransitionFade` 切回登录页。刷新端点自身的 301/401 不在此保证内。
这里还有一个必须单独标注的自举挂起：`NLAuthService refreshLoginWithSuccess:failure:` 通过 `NetWorkManager` 发起 `GET @"/login/refresh"`，首次 `retryCount` 为 0。如果这个 GET 自身返回业务码 301 或 HTTP 401，门面会再次进入 `handleAuthRequired...`；此时外层刷新已经把 `isRefreshing` 置为 YES，且没有刷新端点旁路。该刷新请求会被放入 `pendingRequests` 后返回，`NLAuthService` 的 success/failure 都不会回来，清空刷新窗口和强制登出也不会执行。这是恢复函数重入后的队列挂起，不是当前时序下继续调用 `refreshLogin` 的调用栈递归。

并发不变量：

- `refreshLockQueue` 串行保护 `isRefreshing` 和 `pendingRequests`。
- 一个刷新窗口内只发起一次刷新请求。
- 每个原始请求最多重放一次。
- Cookie 写入由 `NLAuthManager` 统一处理，页面不自行保存凭据。

### 2.4 失败与工程取舍

| 场景 | 当前行为 | 取舍 |
| --- | --- | --- |
| Keychain 迁移写入失败 | 保留旧值，不误删；启动继续按可读凭据判断 | 可能暂时保留 legacy 值，但比迁移中误登出安全 |
| 数据库目录或表初始化失败 | `database` 访问返回不可用，写入回调失败 | 不在启动主线程同步等待所有业务恢复 |
| 缓存迁移/对账失败 | 仍 `markReady`，不阻塞启动；没有“失败后查询一律未命中”的门闩，已有 `AudioCacheInfoTable_v3` 行仍会被查询 | 优先保证播放和 UI 不被启动阻塞；迁移失败只跳过当次目录对账 |
| 普通业务请求的刷新失败 | 恢复器收到 refresh failure，或一次重放后再遇 301/401 时，等待请求失败并发强制登出通知 | `/login/refresh` 自身 301/401 会在 `isRefreshing == YES` 时入队挂起，不进入该收口；需专项修复和验证 |
| App 被系统终止 | background session 由系统管理；进程内对象需下次启动重建 | 不把进程内 context 当成持久任务本身 |

## 3. 链路二：内容发现到播放意图

### 3.1 首页：并发请求、部分成功

关键文件：

- `NLSpotify/Modules/主页面/ViewModel/NLHomeViewModel.m`
- `NLSpotify/Modules/主页面/ViewModel/NLSectionViewModel.m`
- `NLSpotify/Networking/网易云API/为你推荐/NLRecommendAlbumListService.m`
- `NLSpotify/Networking/网易云API/JJAlbum/NLSingerAlbumListService.m`
- `NLSpotify/Networking/网易云API/为你推荐/NLChineseSongListService.m`

首页用一个 `dispatch_group` 并发加载五个候选分区：

1. 为你推荐；
2. 歌手专辑；
3. 华语精品；
4. 欧美；
5. 流行。

每个请求成功后写入固定槽位，失败只 `leave` 不写入。`dispatch_group_notify` 在主线程过滤 `NSNull` 后交付，因此首页可以部分渲染，不会因为单一分区失败而让整页失败。

```text
五个请求并发
  ├─ 成功 → 固定槽位写入 SectionViewModel
  └─ 失败 → 只结束该槽位
                ↓
        group 全部结束
                ↓
       过滤失败槽位 → 主线程展示
```

这是“分区独立失败、整体最终收敛”的设计。它牺牲了严格的五区完整性，换取弱网下页面仍有内容可用。

### 3.2 搜索：输入防抖、分页和结果作废

关键文件：

- `NLSpotify/Networking/网易云API/搜索/NLSearchSuggestService.h`
- `NLSpotify/Networking/网易云API/搜索/NLSearchSuggestService.m`
- `NLSpotify/Modules/搜索页面/Controller/NLSearchResultViewController.m`

Service 与结果页当前覆盖的类型包括：搜索页 UI 展示歌曲、歌单、艺人、歌词四个分段；电台类型由 Service 支持，但不作为当前四段控件之一。

| 类型 | 服务端 type | 当前用途 |
| --- | ---: | --- |
| 歌曲 | `1` | 解析为字典结果，点击后转换为 `NLSong` 播放 |
| 歌单 | `1000` | 渲染原始歌单字典；`didSelect` 没有歌单详情分支。非艺人结果只在 `songId` 非空时播放，原始歌单字典通常没有该字段，所以点击不会进详情，也不应说成已实现播放 |
| 艺人 | `100` | 进入内联 `NLArtistDetailController`，调用 `/artists` 展示 `hotSongs` |
| 歌词 | `1006` | 解析为歌曲结果，点击后转换为 `NLSong` 播放 |
| 电台 | `1009` | `NLSearchSuggestService` 支持；实际广播主入口另外走 `/dj/recommend`，当前不在搜索页四段控件之一 |

搜索状态：

```text
输入文本
  → trim
  → requestToken += 1
  → 清空旧 items、offset=0、hasMore=YES
  → 300 ms dispatch_after
  → token 与 keyword 仍匹配才发第一页
  → offset/limit 分页
  → 滚动接近底部加载下一页
```

`requestToken` 解决的是**结果作废**，不是网络取消。旧请求可能仍在运行。success/failure 更新 UI 前只检查 token 等于当前 `requestToken`，且 callback keyword 等于当前 keyword。离开结果页会递增 token，但回调里没有单独的可见性布尔。

分页记录 `offset`、`hasMore`、`loadingPage`，成功后用 `pageOffset + items.count` 推进偏移量；空结果和失败分别更新状态文案。当前失败态没有接入独立重试按钮。

### 3.3 广播：推荐、兜底、节目和播放

关键文件：

- `NLSpotify/Modules/Advertise/NLAdvertiseViewController.m`
- `NLSpotify/Networking/网易云API/NetWorkManager.m`
- `NLSpotify/Modules/播放器/NLPlayerManager.m`

广播页的当前调用关系：

```text
NLAdvertiseViewController
  → GET /dj/recommend
  → 失败时 GET /dj/hot?limit=20
  → 电台行
  → 内联 NLRadioProgramController
  → GET /dj/program?rid=...&limit=30
  → program.mainSong
  → NLSong
  → NLPlayerManager
```

当前广播页没有接入分类列表、分页和独立重试 UI。推荐电台失败时的热门兜底只替换数据源。节目行只在 `mainSong` 不是字典时返回；它是字典但 `id` 缺失或为空时，仍会构造 `songId` 为空的 `NLSong` 并调用播放器，入口没有歌曲 ID 拦截。

当前艺人详情和广播节目控制器都是对应 `.m` 文件中的内联类，不应在文档中写成尚未存在的独立 `NLArtistDetailViewController`、`NLRadioCategoryViewController` 或 `NLRadioProgramViewController` 文件。

### 3.4 详情页只产生播放意图

歌单、专辑、搜索歌曲/歌词结果、艺人热门歌曲和电台节目最终应落到统一的播放意图入口；搜索歌单结果是当前明确例外，因为结果页尚未实现歌单详情跳转：

```objc
[[NLPlayerManager sharedManager] playWithPlaylist:songs startIndex:index];
```

内容页面不直接创建 `AVPlayer`，也不直接处理 `streaming://`。这样做的边界很明确：

- 页面决定播放哪些 `NLSong`；
- 播放器决定如何取得 URL、命中离线正文或缓存；
- 缓存层决定如何响应字节；
- UI 只订阅状态信号。

### 3.5 内容发现的验证边界

历史计划记录曾对下列接口做过只读探测。2026-10-11 文档对齐没有重放这些请求，也没有保留可打开的响应原文；后续 AI 只能把它们当成历史记录，不能当成当前端点仍可用的证据：

- `/search?type=1`
- `/search?type=100`
- `/search?type=1000`
- `/search?type=1006`

## 4. 链路三：选曲、离线命中与 `AVPlayer`

### 4.1 统一选曲入口

`NLPlayerManager` 的主要入口：

- `playWithPlaylist:startIndex:`：设置播放列表并开始指定歌曲。
- `playSongAtIndex:`：在已有播放列表中切换歌曲。
- `play` / `pause` / `stop`：改变用户播放意图和播放器资源。
- 内部 `playSongAtIndexIfNeeded:`：推进切歌 token、设置当前歌曲、等待缓存 ready。
- 内部 `startSongAfterCacheReady:token:`：按优先级选择离线正文、完整普通缓存或网络播放 URL。
- 内部 `playWithURL:` / `startPlaybackWithURL:cacheKey:token:`：创建流式 `AVPlayerItem`。

选曲状态可以表示为：

```text
playWithPlaylist
  → playlist/currentIndex/currentSong
  → playSwitchToken + 1
  → wantsToPlay = YES
  → 播放状态 Loading
  → 等待 NLCacheManager ready
```

`wantsToPlay` 是公开只读的用户意图，不等于当前 `AVPlayer` 已经在播放。资源尚未 ready 时暂停会将其改为 `NO`；等待数据或系统中断时，意图可能仍为 `YES`。小播放器与全屏播放器的按钮按该意图显示，实际状态与锁屏播放速率则由引擎状态归约，避免缓冲时按钮语义与 toggle 行为相反。

### 4.2 离线优先级

当前歌曲准备阶段的优先级是：

```text
1. NLOfflineAudioStore.localFileURLForSongID:
      → 独立离线正文
2. NLCacheManager.isFullyCachedForURL:cacheKey:
      → 完整普通缓存 .mp3
3. song.playURL
      → 已有播放 URL
4. NLSongService fetchPlayableURLWithSongId:
      → 获取新 URL 后再进入流式播放
5. 以上均失败
      → NLPlaybackStateError
```

离线正文和普通完整缓存都可以直接用本地 `file://` URL 创建 `AVPlayerItem`。完整普通缓存命中时，即使当前 `NLSong` 没有新的播放 URL，也可以通过 `songId` 找到已完成缓存记录；这也是为什么缓存账本需要保留 `songId`。

### 4.3 `playSwitchToken`：结果作废而不是网络取消

`playSwitchToken` 是单调递增的播放上下文版本号。切歌、停止、媒体服务重置和基于新 URL 建立资源都会推进它，异步闭包捕获创建时的 token：

```objc
NSUInteger token = ++self.playSwitchToken;

// 回调回主线程后
if (token != self.playSwitchToken) return;
if (self.currentSong != expectedSong) return;
```

token 直接保护的迟到结果是：

- 播放 URL 请求成功/失败；
- 缓存 ready gate 放行；
- ResourceLoader 缓存进度；
- 周期性时间观察器；
- item/player KVO 回主线程后的处理；
- 媒体服务重置后恢复位置的 seek 回调。

KVO 同时核对当前 player 与 item，播放结束通知仍以当前 item 身份检查为准。音频会话配置、激活与停用在独立串行后台队列执行；回主线程使用 `audioSessionGeneration` 丢弃停止、中断、重置之前的迟到结果，不能仅依赖播放 URL 的 token。

旧 ResourceLoader 会被 `invalidateAndCancelAll` 取消，但 token 仍然需要保留，因为取消和回调到达之间存在窗口。**取消减少无效工作，token 保证迟到结果无效；两者不能互相替代。**

### 4.4 `AVPlayerItem` 身份保护

除 token 外，播放器保存 `currentPlayerItem`、`observedItem`、`observedPlayer` 和 `timeObserverOwner`：

- 切歌、替换音源、停止及媒体服务重置共用 `tearDownCurrentPlaybackReleasingPlayer:`；
- 在原 `timeObserverOwner` 上显式移除周期观察，再释放 owner，不能向新 player 移除旧 token；
- 从原 item/player 上移除 KVO，并移除结束通知；
- dispose 缓存进度订阅，取消并释放旧 Loader，再清空 item，按需释放 player；
- KVO 和周期回调校验 token 与 player/item 身份，结束通知检查当前 item；
- Manager 释放时注销系统通知和自身远程命令 targets；远程命令注册幂等，不能清除别的 owner 的 targets。

因此快速“歌曲 A → B → C”时，A 的 KVO 即使迟到，也不能改写 C 的 item 状态。订阅者不要等待 `NLPlaybackStateEnded`：枚举里有这个值，但自然结束路径没有赋值。

### 4.5 状态与播放历史

播放状态枚举为：

```text
Idle → Loading → Playing / Paused / Error
自然播放结束不会发出 NLPlaybackStateEnded
  → 单曲循环：seek 到 0 并在 wantsToPlay 时继续 play
  → 列表循环 / 随机：直接 playNext
```

正常业务路径中，`Playing` 只由 `AVPlayer.timeControlStatus == Playing` 且用户意图允许、未处于中断时发布，不能从 item Ready 直接推断。`Loading` 复用为资源准备、等待数据、等待音频会话激活或恢复定位；用户暂停及中断期间发布 `Paused`。资源失败或会话配置/激活失败发布 `Error`，停止后为 `Idle`。

状态进入 `NLPlaybackStatePlaying` 时，以当前 `playSwitchToken` 去重，只为同一 token 记录一次播放历史。状态现在跟随引擎实际运行，但不是扬声器已出声或用户实际收听时长的证明；仅点击歌曲或创建 `AVPlayerItem` 不写历史。

播放器还负责：

- 列表循环、单曲循环和随机播放；
- `AVAudioSessionCategoryPlayback`；
- `MPRemoteCommandCenter` 播放、暂停、上一首、下一首和进度拖动；
- `MPNowPlayingInfoCenter` 标题、艺人、封面、时长和当前进度。

### 4.6 系统音频事件与恢复

- 通过兼容 iOS 26.1 的 `AVAudioSessionInterruptionNotification` 处理 begin/end。begin 暂停引擎、保留意图；end 仅在系统给出 ShouldResume 且用户意图未被暂停、停止或路由变化取消时恢复。重复 begin 与无对应 begin 的 end 不启动新播放。
- `OldDeviceUnavailable` 读取 `AVAudioSessionRouteChangePreviousRouteKey` 的旧输出：耳机、蓝牙及其他外部输出消失时暂停并取消恢复意图，避免自动外放；旧输出明确只有内置扬声器/听筒时不主动暂停，缺少旧输出信息时保守暂停。连接新设备不主动恢复。
- 媒体服务重置推进 token，统一释放旧引擎与观察者，保留当前歌曲、列表、已解析来源和有效位置，重新配置音频类别，但不自动启动播放。用户再次点击播放后重建 player/item，恢复位置；seek 回调校验新上下文。
- `setCategory`、`setActive` 等可能阻塞的会话操作放到 `com.nlspotify.audio-session` 串行后台队列，结果回主线程协调；被停止或重置取消的旧激活不会直接触发旧 item 播放。
- 监听 `UIApplicationDidBecomeActiveNotification`，回到前台时按当前 player/item、播放意图及中断标记重新归约状态，刷新 Now Playing，并向界面补发当前进度快照；仅同步，不因为进入前台而自动播放。
- 用户或远程命令 seek 统一在主线程协调；成功完成后核对 `playSwitchToken`、原 player 和 item 身份，补发实际进度并刷新状态及 Now Playing。取消或过期的 seek 不发布结果，暂停状态下拖动也不依赖周期回调刷新锁屏进度。
- `Playback` 默认非混音，不等于独占全部系统声音；普通暂停保留会话，`stop` 停用并通知其他会话可以考虑恢复。后台声明不保证永久保活，系统媒体灵动岛也不是可保证出现的自定义界面。

依据：[Apple 音频中断](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions)、[路由变化](https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes)、[媒体服务重置](https://developer.apple.com/documentation/avfaudio/avaudiosession/mediaserviceswereresetnotification)、[周期观察移除](https://developer.apple.com/documentation/avfoundation/avplayer/removetimeobserver(_:))。

## 5. 链路四：`AVAssetResourceLoader` 与三级缓存

### 5.1 字节链路总图

```text
AVPlayerItem
  → AVURLAsset(streaming://...)
  → AVAssetResourceLoaderDelegate
  → NLResourceLoader
       ├─ L1：NLAudioMemoryCache，热点内存 segment
       ├─ L2：缓存目录/*.tmp + WCDB Range ledger
       ├─ L3：缓存目录/*.mp3，完整普通缓存
       └─ Origin：真实 HTTP URL + 有界 Range 请求
```

这不是把 HTTP 响应整体下载后交给 AVPlayer，而是由 AVPlayer 提出区间需求，Loader 尽量用本地连续字节满足；本地出现缺口时，只请求当前连续缺口。

### 5.2 ResourceLoader 的入口与边界校验

`NLPlayerManager` 把真实 URL 的 scheme 替换为 `streaming`，但保留 origin URL 注入 `NLResourceLoader`：

```text
真实 https/http URL
  → URLComponents.scheme = streaming
  → AVURLAsset
  → asset.resourceLoader.setDelegate(loader, serial queue)
  → loader.originURL = 真实 URL
```

`shouldWaitForLoadingOfRequestedResource:` 负责：

1. 检查 origin URL、data request 和 content-information request 是否有效；
2. 拒绝负 offset。只有非 `requestsAllDataToEndOfResource` 的 data request 才拒绝 `requestedLength <= 0`；请求到末尾时允许非正 length，并把结束位置设为 `LLONG_MAX`。
3. 只有明确长度的请求才检查 `requestedOffset + requestedLength` 是否溢出 `LLONG_MAX`。
4. 已知账本总长度时，把结束位置截到资源末尾；总长度未知且请求到末尾时，结束位置保持 `LLONG_MAX`。这不是固定分块上限。
5. 登记 request context，等待 `NLCacheManager` ready；
6. 通过 `processingQueue` 串行处理该 loading request。

取消时，`didCancelLoadingRequest:` 会标记 context、移除映射并取消对应 `NSURLSessionDataTask`。已完成的写入区间仍可在取消后合并到账本，但不会继续向已经取消的 AVFoundation 请求交付数据。

### 5.3 本地连续区间读取

`serveLocalDataForRequest:` 每次本地读取最多约 512 KiB。这个上限只约束本地读取，不约束随后的 Origin HTTP Range 长度。

1. 先向 `NLAudioMemoryCache` 请求当前 offset 的连续 segment；
2. 内存未命中时查询 WCDB `cachedRangesString`；
3. 只有当前 cursor 落在已缓存区间内才从文件读取；
4. 完整 `.mp3` 用完成文件，未完成记录用 `.tmp`；
5. `open + pread` 读取指定 offset；
6. `respondWithData:` 返回 AVPlayer，并把磁盘读取结果回填 L1；
7. 读到区间末端后再判断下一个连续区间，遇到空洞立即进入回源。

使用 Range ledger 而不是文件长度判断连续性，是因为拖动播放可能形成空洞：文件物理长度可以已经超过某个 offset，但中间字节并不一定已经有效写入。

`pread` 允许多个读操作使用明确 offset，不依赖共享文件描述符的游标；但它仍然会把数据读入用户态 buffer，不能将这条路径表述成绝对零拷贝。

### 5.4 Origin Range 回源与响应校验

本地无法继续满足时，Loader 计算：

```text
cursor = 当前连续已满足位置
nextLocalOffset = 内存或磁盘下一个已缓存区间起点
fetchLength = nextLocalOffset - cursor
```

随后按缺口创建 HTTP Range 请求。512 KiB 不是这个请求的上限：`fetchLength = nextLocalOffset - cursor`，总长度未知且请求到末尾时，`endOffset` 可以是 `LLONG_MAX`，网络请求因此可能非常大。

```http
Range: bytes=<cursor>-<cursor + fetchLength - 1>
Accept-Encoding: identity
```

`NLHTTPRangeValidator` 对 206 要求可解析且与请求起点匹配的 `Content-Range`。对 200 不要求 `Content-Range`，但只接受请求起点为 0 且 `expectedContentLength > 0`。响应无效、数据不足、URL 不可创建或任务被取消时，当前 loading request 以错误结束，不把不可信字节写入缓存。

网络数据到达后同时执行三件事：

1. 将合法子区间交给 `AVAssetResourceLoadingDataRequest`；
2. 写入 L1 内存 segment；
3. 用 `pwrite` 写入 L2 `.tmp`，完成后记录 session range。

当前任务完成后，Loader 等待该请求关联的写入 group，再继续处理后续缺口；这样不会因为网络回调先结束而让账本落后于已经交付的字节。

### 5.5 L1/L2/L3 的责任边界

| 层级 | 内容 | 解决的问题 | 生命周期 |
| --- | --- | --- | --- |
| L1 | `NLAudioMemoryCache` segment | 热点重复读取和快速响应 | `NSCache`，`totalCostLimit` 12 MiB，`countLimit` 512，另受内存警告影响 |
| L2 | `.tmp` + `NLAudioCacheInfo.cachedRangesString` | 断点区间复用、拖动空洞、进程重启后恢复 | 未完成文件合计达到 128 MiB 后，按最近访问时间裁到 90% |
| L3 | `.mp3` + `isFinished=YES` | 完整普通缓存直接播放和按歌曲 ID 命中 | 完整文件合计达到 500 MiB 后，按最近访问时间裁到 90%；启动和进后台不触发 |
| Origin | HTTP Range | 本地缺口回源 | 受网络、服务器 Range 语义和 URL 有效期影响 |

L1 的内存约束和分段数量由 `NLAudioMemoryCache` 独立控制。L2/L3 的容量账本在启动对账和显式清空后重建；只有后续缓存写入使对应层达到高水位，才在 admission queue 上调度该层 LRU。保护集合包含当前播放、活动写入、下载中和已完成下载关联的缓存记录。

### 5.6 缓存身份：稳定 key、SHA-256 与旧表迁移

当前播放器会先调用 `cacheIdentityForURL:cacheKey:`，再由 `identifierForURL:cacheKey:` 对得到的字符串做 SHA-256。分三种输入：

```text
有 songId，且 URL 的 host 或 path 非空：
cacheIdentity = songId + "\\n" + lower(host) + path
identifier    = "sha256-" + sha256(cacheIdentity)

有 songId，但 URL 为空或 host/path 都空：
cacheIdentityForURL 只返回 songId。
无 URL 的完整缓存查询不使用 sha256(songId) 当文件名，而是按 songId 列选择
isFinished、totalLength > 0、文件大小等于 totalLength、lastAccessTime 最新的一行，
再使用该行已有的 cacheIdentifier。

没有 songId：
identifier = "sha256-" + sha256(url.absoluteString)
这条 legacy 路径包含 query。
```

- 稳定身份只拼接小写 host 和 path，不包含 query。接口注释写 “Query tokens are ignored”，但实现没有验证 query 是否为签名参数；不要把“签名 URL”说成当前协议事实。
- 无稳定 key 时才对完整 URL 做 SHA-256，此时 query 会参与身份。
- 文件名前缀为 `sha256-`，十六进制为小写。
- 标识分片写入使用 8 条按 identifier 哈希的串行队列；准入还有单独的 admission queue，清理扫描会再派到 utility 队列。不能说所有缓存操作只有这 8 条队列。
- WCDB 新表为 `AudioCacheInfoTable_v3`，主键为 `cacheIdentifier`。

旧表 `AudioCacheInfoTable` 的 `urlMD5` 行迁移为 legacy `cacheIdentifier`，保留旧文件名，不把旧 partial 区间强行合并到新 SHA 身份。具备 `songId` 的旧完整缓存仍可通过“按歌曲寻找完整缓存”继续播放；旧 partial 在身份不匹配时不作为新账本的连续区间。

这条迁移策略的取舍是：

- **安全**：不把可能来自不同 URL 变体的 partial bytes 混在一起；
- **兼容**：尽可能继续使用旧的完整音频文件；
- **代价**：旧 partial 可能被重新下载，缓存空间也可能暂时存在两套身份。

### 5.7 完整缓存晋级与启动对账

普通缓存从 `.tmp` 晋级为 `.mp3` 必须满足：

```text
Range ledger 覆盖 [0, totalLength)
  + .tmp 文件长度 == totalLength
  + fsync 成功
  + rename(.tmp, .mp3) 成功
  + WCDB isFinished 更新成功
```

完成判定统一为：`isFinished=YES`、Range ledger 无空洞覆盖整首、`.mp3` 长度与正数 `totalLength` 一致。按 URL 查询、按歌曲 ID 查找、写入保护和启动对账均复用同一判定；仅有完成标记或扩展名不能作为本地完整文件命中。

逻辑上区分“部分可读”“字节完整但尚未提交完成”“已提交完整缓存”，不新增数据库状态枚举。`cachedRangesCoverFullLength...` 仍仅表示区间覆盖，不代表完成状态已提交。晋级接口的成功回调只表示完整缓存已提交，或原本就是有效完整缓存；重复完成调用幂等返回成功。

WCDB 提交失败时，恢复内存中的完成标记与访问时间，并尝试将 `.mp3` rename 回 `.tmp`，返回失败且不发布完成通知。反向 rename 是尽力回滚；失败后保留完整账本与已改名正文，允许后续显式完成或启动对账重试。正文改名成功不等于数据库提交成功。

启动对账处理：

- 有效的已提交 `.mp3`：保留，移除同身份残留 `.tmp`；
- `.tmp` 和完整账本、匹配长度同时存在：走相同晋级协议补交完成状态；普通 partial 继续保留；
- `.tmp` 不存在、`.mp3` 存在且账本完整、长度匹配：补交完成状态；
- 可恢复正文的元数据提交失败：保留候选，但不作为完整缓存命中；
- 无可恢复正文的错误完成记录、无对应账本的文件：清理；
- 容量统计与淘汰按实际 `.tmp`/`.mp3` 文件占用分桶，不把容量桶当成可播放状态判定。

这仍不是跨文件系统和 WCDB 的原子事务。长度匹配与区间覆盖不能发现同长度内容损坏；当前没有内容 hash 校验。运行时共享区间索引和现有进度条表现未在此次修改。

2026-10-20 状态协议回归：新增五个场景先失败，修复后扩展 `NLSpotifyTests` 113 项通过，0 failure、0 runtime warning；命令排除了此前已知的 Keychain entitlement 失败项 `testKeychainCredentialPersistsAcrossStoreInstances`。无签名模拟器验证不代表真机故障恢复或性能测量。

同轮实际 App smoke 使用真实 MP3 夹具及临时原生探针调用缓存、播放器路径：重复完成成功，创建的是 `file://` 资产，`resourceLoader` 为 nil，`AVPlayerItem` 达到 ReadyToPlay，驱动该 AVPlayer 后播放时间前进。探针不覆盖真实 CDN、真机后台、完整 UI 操作或性能对比，临时探针已在验证后清理。

### 5.8 ready gate、写入所有权与清空屏障

`NLCacheManager` 初始化后在 Utility 队列：

1. 创建缓存目录；目录失败会直接 `markReady` 并返回。
2. 迁移缓存账本；迁移失败会记录日志并跳过目录对账。
3. 迁移成功才执行目录对账。
4. 无论对账是否执行，`@finally` 都会 `markReady`，异步放行等待中的请求。迁移或目录失败不会安装未命中门闩；之后的查询仍读 `AudioCacheInfoTable_v3`，表里已有的行不会因为这次失败自动变成 miss。

ResourceLoader、播放器、缓存列表和下载迁移都可以通过 `whenReadyOnQueue:perform:` 登记，不需要在启动或网络 delegate 队列使用 semaphore / `dispatch_group_wait` 阻塞。

写入保护包括：

- 以 cache identifier 分片的串行队列；
- `activeWriteCounts` 记录正在写入的文件；
- `cacheGeneration` 让“清空之前提交”的旧写入在执行时失效；
- clear barrier 等待已登记操作完成，再删除文件、L1 和账本；
- 清空期间的新写入暂存，清空结束后再放行。

普通缓存容量淘汰不在启动或进后台触发。L2 高水位 128 MiB、L3 高水位 500 MiB，都只裁超限的那一层，目标是该层高水位的 90%。保护集合包含当前播放、活动写入、下载中和已完成下载关联的缓存记录。离线正文不在普通缓存目录中，因此普通 LRU 不负责删除它。

## 6. 链路五：显式下载、离线正文与所有权

### 6.1 为什么显式下载不能复用普通 Range 缓存

在线播放缓存和用户主动下载虽然都最终产生音频字节，但所有权不同：

| 对象 | 普通播放缓存 | 用户离线资产 |
| --- | --- | --- |
| 目的 | 加速下一次播放 | 用户明确要求保留并离线播放 |
| 文件位置 | `Caches/NLAudioCache` | `Application Support/NLOfflineAudio` |
| 淘汰策略 | LRU、可被清理 | 不应被普通缓存清理删除 |
| 完成语义 | Range ledger 完整 + 文件长度匹配 | 系统下载完成 + 正文导入 + 离线元数据 + WCDB 事务 |
| URL 依赖 | 可按 URL 变体和歌曲 ID命中 | 以 `songId` 为资产所有权主键 |
| AVFoundation 路径 | ResourceLoader 或完整缓存 file URL | 独立本地 file URL |

如果把“普通缓存完整”直接写成“用户下载完成”，就会出现：LRU 删除了下载正文、旧任务覆盖新任务、WCDB 状态与文件所有权不一致等问题。

### 6.2 background session 入口

关键文件：

- `NLSpotify/Modules/播放器/NLDownloadManager.m`
- `NLSpotify/Modules/播放器/NLOfflineAudioStore.m`
- `NLSpotify/Modules/WCDB/上层仓库/NLDownloadRepository.mm`
- `NLSpotify/App/AppDelegate.m`

当前 background session：

```text
identifier = com.nlspotify.offline-downloads
configuration = backgroundSessionConfigurationWithIdentifier:
sessionSendsLaunchEvents = YES
taskDescription = songId
```

`AppDelegate` 的 `handleEventsForBackgroundURLSession` 把系统交付的 completion handler 转给 `NLDownloadManager`。管理器使用同一个 identifier 创建 session，调用 `getAllTasksWithCompletionHandler:`，通过 `taskDescription` 找回 `songId` 和 WCDB 下载记录。

background session 接收真实 HTTP/HTTPS URL；`streaming://` 只留在播放链路，不直接交给系统下载任务。

### 6.3 下载状态机

```text
用户点击下载
  → 若 background task 恢复尚未结束：只放进内存 pendingSongsByID，不写 WCDB pending 状态
  → 恢复结束后才调用 addDownloadForSong:
  → WCDB status = downloading
  ├─ pause → paused + resumeData
  ├─ cancel → 恢复状态清除成功才是 cancelled，清除失败记 failed
  ├─ 网络/导入/持久化失败 → failed
  └─ 正文导入和数据库提交成功 → completed

failed / cancelled / paused
  → retry
  → 清理旧恢复数据
  → 新 generation
  → downloading
```

管理器以 `songId` 去重；同一歌曲在恢复、重试、用户新建任务之间只能有一个 active reservation。启动恢复尚未结束时，新下载进入内存中的 `pendingSongsByID`，不会先写成数据库 `pending`。不要在 `DownloadQueueTable` 里寻找 `pending` 状态。

### 6.4 generation 所有权

每个下载 reservation 具有递增 generation。context 字典保存：

- `songId`；
- generation；
- `url` 和 `song`；
- `cancelled`；
- received/expected bytes；
- `usedResumeData`。

task identifier 不是 context 字段，而是 `taskContextMap` 和 `taskMap` 的 key。导入结果也不存在 context 里，完成回调另行判断导入是否成功。

delegate 回调首先检查：

```text
context 仍属于 task
+ context 未取消
+ songId 当前 reservation generation 相同
```

不满足时，迟到的进度、完成或失败回调直接丢弃。这个保护覆盖：暂停后旧 task 回调、取消后系统完成回调、重试后旧 generation 回调，以及 App 启动恢复期间的任务重建。

### 6.5 完成不变量

下载完成不是 `didCompleteWithError == nil` 就结束，而是以下顺序：

```text
系统临时文件
  → NLOfflineAudioStore.importCompleteAudioAtURL:forSongID:
       ├─ 检查 file URL 和非空文件
       ├─ 写入 downloads.json 元数据
       ├─ 移动到独立离线目录
       └─ 设置排除备份
  → NLDownloadRepository.completeDownloadWithSong:
       ├─ DownloadQueueTable.status = completed
       └─ DownloadedSongsTable 写入歌曲
          （同一 WCDB transaction）
```

`NLOfflineAudioStore` 使用：

```text
Application Support/NLOfflineAudio/downloads.json
Application Support/NLOfflineAudio/<songId-derived>.audio
```

`resumeData` 以 Base64 形式保存到 JSON；task identifier、已接收字节和预期字节也保存在同一资产账本中。

任何以下失败都不能伪造 `completed`：

- 系统临时文件为空或不可读；
- 离线目录/元数据写入失败；
- 文件移动失败；
- 下载队列状态事务失败；
- `DownloadedSongsTable` 写入失败；
- task 已被取消或 generation 已失效。

失败路径会把队列项更新为 `failed` 或 `cancelled`；某些启动迁移或持久化失败路径还会清理对应的已下载歌曲记录。普通下载完成事务失败不能概括为“总会清理下载歌曲记录”，用户仍可重试。

### 6.6 暂停、恢复、取消和删除

- **暂停**：调用 `cancelByProducingResumeData:`，只有 resume data 非空且 JSON 写入成功才进入 `paused`。
- **恢复**：读取 `paused` 记录和 resume data，使用 `downloadTaskWithResumeData:` 创建新任务，并获得新 reservation generation。
- **重试**：允许 `failed`、`cancelled`、`paused`，先清理旧恢复状态，再创建新任务。
- **取消**：取消 task，并尝试清除 task context 和恢复状态。只有恢复状态清除成功，数据库才置为 `cancelled`；清除失败置为 `failed`。
- **删除单首**：列表页先调用 `removeOfflineDownloadForSongID:` 取消任务并删除离线正文/恢复元数据，再由 `NLDownloadRepository` 和 `NLSongRepository` 分别删下载队列行和已下载歌曲行。这个管理器方法本身不删 WCDB，也不删普通播放缓存。
- **一键清空**：首页抽屉确认后依次 `stop`、`removeAllOfflineDownloads`、`clearAllCache`、清空下载队列和已下载歌曲表。不要把这整条链写进 `NLDownloadManager`；管理器只负责取消任务和清空离线目录。

系统可以在 App 被挂起或进程终止后交付 background session 事件，但当前本地测试不等于物理设备上的系统后台交付证明；用户 force-quit、resume data 失效和真实 CDN 行为仍需单独验证。

## 7. 链路六：ReactiveObjC 状态传播与页面一致性

### 7.1 状态源

`NLPlayerManager` 对外公开五个信号：

| 信号 | 内容 | 主要消费者 |
| --- | --- | --- |
| `playbackStateSignal` | 实际会发出 `Idle/Loading/Playing/Paused/Error`；枚举有 `Ended`，自然结束路径不赋值 | 小播放器、全屏播放按钮、锁屏信息 |
| `songSignal` | 当前 `NLSong` | 标题、艺人、封面、歌词、收藏状态 |
| `progressSignal` | 0 到 1 的播放进度 | 进度条、当前时间、歌词行定位 |
| `cacheProgressSignal` | 0 到 1 的缓存进度 | 缓冲条、完整缓存提示、下载/缓存 UI |
| `hasPlaylistSignal` | 是否存在播放列表 | TabBar accessory 是否显示 |

播放器通过 KVO 观察 `AVPlayerItem.status` 与 `AVPlayer.timeControlStatus`，周期观察在主队列产生进度，通过结束通知调度下一首。Ready 只表示资源就绪，不直接发布 Playing；按钮读取 `wantsToPlay`，锁屏速率读取实际状态。

### 7.2 UI 更新规则

ResourceLoader 的数据回调不保证在主线程。引擎 KVO 和系统事件统一回主线程协调，周期观察直接在主队列执行；音频会话配置/激活在串行后台队列执行。UI 消费者继续保留主线程更新约束：

```text
ResourceLoader / KVO / 系统音频事件 / 后台会话结果
  → 主线程校验播放上下文并归约状态
  → NLPlayerManager subject
  → 页面读取状态及 wantsToPlay，更新 UIKit
```

`NLMusicPlayerViewController` 的更新还要满足当前页面和当前歌曲约束：

- 歌曲变化时重置标题、封面、时间、缓存进度和歌词；
- 缓存 ready 回调确认 `currentSong` 仍是捕获的歌曲；
- 进度拖动期间不让周期信号覆盖用户手势；
- 失败的收藏查询用 `favoriteStateRequestToken` 和 song ID 过滤；
- 页面消失时歌词请求失效。
TabBar、小播放器和全屏播放器的 UI 订阅都接了 `takeUntil:self.rac_willDeallocSignal`。`@weakify/@strongify` 仍然只处理 block 引用，取消订阅靠 `takeUntil`。`NLPlayerManager` 对 ResourceLoader 的 `cacheProgressDisposable` 仍在切歌时显式 dispose。已经 `dispatch_async` 出去的 block 仍可能再跑一次，页面内的 song ID 和 token 检查还要留。

### 7.3 进度和缓存进度不能混为一谈

播放进度描述“AVPlayer 当前时间 / 总时长”；缓存进度描述“Range ledger 覆盖的字节 / 总长度”。

- 播放进度可能已经接近 0.8，但缓存只覆盖前半段；
- 缓存进度为 1 时，普通完整缓存可以直接 file URL 播放，但不表示用户下载状态为 completed；
- 离线正文命中时，播放器将缓存进度展示为 1，但其所有权仍属于 `NLOfflineAudioStore`。

分开信号可以避免 UI 把“播放到 80%”误显示成“已缓存 80%”，也避免把普通缓存提示误当下载完成。

## 8. 辅助链路：歌词、评论与搜索历史

### 8.1 歌词：行级 LRC 与请求代次

关键文件：

- `NLSpotify/Modules/播放器/播放器页面/NLMusicPlayerViewController.m`
- `NLSpotify/Modules/播放器/播放器页面/NLLyricLine.m`
- `NLSpotify/Networking/网易云API/音乐播放Url/NLSongService.m`

当前歌词流程：

```text
songSignal
  → invalidatePendingLyricRequests
  → 清空旧歌词行
  → currentLyricSongId = song.songId
  → 只有 lyricVisible 为 YES 才 beginLyricRequest 并请求歌词
手动点封面且当前没有歌词行
  → beginLyricRequest
  → NLSongService fetchLyricWithSongId:
回调回到主线程
  → 校验 lyricPageVisible + songId + requestToken
  → 正则解析 LRC
  → 多时间标签展开并排序
  → 播放进度更新当前行
```

自动请求的门槛是歌词面板可见（`lyricVisible`），不是播放页仅仅处于前台。回调校验用的是播放页可见（`lyricPageVisible`）、song ID 和 token。收起面板、切歌、离开播放页或开始新请求都会递增 token；过期 success/failure 不更新歌词、不打开面板、不弹失败提示。

解析范围：

- 支持带两位分钟、两位秒和两/三位小数的行级时间标签；
- 一行多个时间标签会展开成多条 `NLLyricLine`；
- 正常播放从当前行继续线性查找，快退时从头查找；
- 当前行变化时刷新歌词表。

当前限制：不支持逐字歌词、翻译歌词、歌词持久化、二分查找，以及不带小数的 `[mm:ss]`、`[offset:...]` 等扩展格式。

`NLSongService` 对播放 URL 只接受可解析的非空 HTTP(S) URL；空链接、非法文本和上游拒绝统一转换为错误，不用固定外链或 `403` 文本启发式拼接。

### 8.2 评论：异步排版、布局缓存与自适应行高

关键文件：

- `NLSpotify/Modules/评论区/TextFoldHelper/NLCommentTextFolder.m`：TextKit 行计数和组合字符安全截断；
- `NLSpotify/Modules/评论区/TextFoldHelper/NLCommentTextLayout.m`：不可变双态文本与文本高度；
- `NLSpotify/Modules/评论区/TextFoldHelper/NLCommentLayoutCoordinator.m`：异步任务合并、缓存与失效；
- `NLSpotify/Modules/评论区/NLCommentCell.m`：应用布局结果，不在布局回调中排版；
- `NLSpotify/Modules/评论区/NLCommentListViewController.m`：准备分页、环境失效、增量插入和阅读锚点。

评论是歌曲、歌单和专辑的只读分页列表，当前链路：

1. 主线程取得真实 table 行宽，通过 Cell 共用的布局规则扣除 74pt 水平占用；与实际 `contentLabel` 宽度一致，不用屏幕宽度猜测。捕获正文、字体和 display scale 快照。
2. `NLCommentLayoutCoordinator` 使用最多 2 个并发任务计算；TextKit 对象只由所在任务使用，不在工作线程操作视图。同一布局键合并在途任务。
3. 用 TextKit 判断是否超过三行，并在 composed-character boundaries 上二分查找加入 `...展开` 后仍能放下的前缀。最终富文本的高度使用字符串绘制测量以匹配 UILabel 的混排字体度量，再按像素向上取整；不是直接把 `NSLayoutManager.usedRect` 当成 UILabel 的高度。
4. 不可变 `NLCommentTextLayout` 保存正文、精确宽度、字体、折叠/展开富文本和两种文本高度；键覆盖内容、宽度、字体描述和 scale。协调器的 `NSCache` 设置 256 项、8 MiB 文本估算 cost 的限制；当前已加载页的有效布局另外由页面持有，不代表整个列表的总内存有严格上限，也不是全局 LRU。
5. 回主线程检查页面代次、模型身份及内容快照；页面离开、宽度/字号/scale 变化使旧工作失效，缓存命中的异步回调也必须通过代次检查。结果准备完成后才把新页暴露给列表，追加页只插入新增行；环境重排阶段显示加载状态，不使用旧尺寸。
6. Cell 应用缓存的正文高度约束，整行高度仍由主线程 Auto Layout 计算；移除 Model 的旧整行高度和富文本缓存，不再依赖 `willDisplayCell` 写回。宽度、字体变化统一重排，展开状态保留在当前评论模型上。
7. 长评论保留整段正文点击切换的产品行为，短评论不触发切换。普通展开/收起只更新缓存文本和高度约束，再无动画批量更新行高，由 UITableView 协调 self-sizing 和滚动偏移，不再捕获/恢复整表锚点，避免二次补偿推动上方评论。分页和整体环境重排仍使用现有阅读锚点路径，两类操作不能混用同一套补偿。正文提供 VoiceOver 展开/收起自定义操作，复用时清理动作、引用并取消旧头像请求。

## 9. 链路七：WCDB、迁移、事务与文件系统一致性

### 9.1 数据库初始化

关键文件：

- `NLSpotify/Modules/WCDB/NLDataBaseManager.mm`
- `NLSpotify/Modules/WCDB/上层仓库/NLSongRepository.mm`
- `NLSpotify/Modules/WCDB/上层仓库/NLDownloadRepository.mm`
- `NLSpotify/Modules/WCDB/上层仓库/NLPlayListRepository.mm`
- `NLSpotify/Modules/WCDB/上层仓库/NLSearchRepository.mm`

数据库路径：

```text
Library/Application Support/NLSpotify/NLSpotify_v2.sqlite
```

`NLDataBaseManager` 创建一个 serial `writerQueue`，数据库第一次真正访问时：

1. 创建 Application Support 下的应用数据库目录；
2. 新位置没有主库且 `Documents/NLSpotify_v2.sqlite` 存在时，通过 WCDB `moveFilesToDirectory:` 迁移主库、WAL、SHM、journal 和修复材料；失败则停止本次初始化，后续访问可重试，不创建空库替代；
3. 打开新位置的 WCDB；已有目标库时直接使用，不用旧库覆盖，也不自动删除旧库；
4. 创建业务表和 `DatabaseSchemaVersionTable`，执行 `migrateSchemaIfNeeded:`；
5. 设置 `databaseReady`。显式路径初始化用于隔离测试，不会触碰默认 Documents 数据。

当前 schema version 为 1。旧播放历史迁移在同一 WCDB transaction 中把歌曲实体转成 `PlaybackHistoryMetadataTable`，默认 `playCount=1`、`lastPlayedAt=0`，最后写入 schema version。版本高于当前 App 时拒绝继续迁移，避免低版本误读新结构。

缓存账本迁移是单独的 `migrateCacheLedgerIfNeededWithCompletion:`：旧 `AudioCacheInfoTable` 的 `urlMD5` 行先复制到 `AudioCacheInfoTable_v3`，逐行核对关键字段后删除旧表。迁移失败只跳过当次目录对账，不会禁止后续读取 v3；不要把“迁移失败”理解成查询层自动全部未命中。

2026-10-20 目录迁移验证：仓库与迁移回归 13/13 通过；扩展 `NLSpotifyTests` 回归 108 项通过、0 failure、0 runtime warning（运行命令排除了此前已知因无签名 Keychain entitlement 失败的 `testKeychainCredentialPersistsAcrossStoreInstances`，不代表该项已修复）。模拟器实际启动 App 后，新目录存在主库、WAL 和 SHM，Documents 目录为空。此证据不覆盖物理设备或迁移过程中强制终止。

### 9.2 Repository 的读写边界

`NLDataBaseManager` 提供：

- `performWrite:`：在 writer queue 执行单次写；
- `performWriteTransaction:`：在 writer queue 执行 WCDB transaction；
- `performRead:`：派发到同一条 writer queue 取快照，再把结果回调到指定队列；它不是独立只读队列。

页面不直接拼 WCDB 表名和条件。Repository 负责：

- 输入 ID 校验；
- 实体快照；
- 表间关系；
- 事务边界；
- 主线程完成回调。

这只覆盖 Repository 入口。`NLCacheManager` 的缓存账本 insert/delete 在 identifier 分片队列里直接使用 `database`，不调用 `performWrite:` 或 `performWriteTransaction:`。因此不能说所有 WCDB 访问都被 writer queue 串行化。

同步读取 API 仍存在，调用方需要自己在后台使用；面向列表的批量筛选和排序已经尽量先取快照，再回主线程应用，避免在主线程进行整表排序或逐首读取访问时间。

### 9.3 事务案例

#### 播放历史

歌曲实体与 `NLPlaybackHistoryMetadata` 分离：歌曲保存展示数据，metadata 保存 `lastPlayedAt` 和 `playCount`。播放器进入 Playing 时按 token 触发 Repository 写入，避免点击即写入。

#### 歌单关系

`NLPlayListRepository` 的加歌/删歌/删歌单在同一 writer transaction 内处理：

```text
歌单存在性校验
  → LocalSongsCacheTable 写入/读取
  → PlayListSongRelationTable 添加或删除关系
  → 必要时更新封面
  → 删除后检查孤立本地歌曲
```

重复加歌是幂等的；删除关系后，如果歌曲没有被其他歌单引用，才删除本地歌曲实体。任一步失败，WCDB transaction 回滚。

#### 下载完成

`NLDownloadRepository.completeDownloadWithSong:` 在同一 transaction 中更新：

- `DownloadQueueTable.status = completed`；
- `DownloadedSongsTable` 的歌曲记录。

但它不能覆盖文件系统。因此调用方必须先完成离线正文导入，不能只因为数据库事务成功就推断音频文件存在。

#### 缓存 Range 账本

缓存数据写入包含 `.tmp` 的 `pwrite` 和 WCDB Range 账本更新，但它们不是一个跨系统事务。启动对账、长度检查、generation 和失败回滚只是在工程上缩小不一致窗口，不能声称提供数据库与文件系统的强原子性。

| 数据 | 表/Repository | 关键事实 |
| --- | --- | --- |

## 10. 并发控制与失败收口总表

| 并发/一致性问题 | 控制手段 | 保护对象 | 失败结果 |
| --- | --- | --- | --- |
| 快速切歌 | URL、缓存进度、周期进度与 item/player KVO 使用 `playSwitchToken`，并校验对应 player/item 身份 | URL、KVO、时间观察器、缓存进度 | 丢弃旧上下文回调；结束通知仍以当前 item 身份过滤 |
| 搜索竞态 | `requestToken` + keyword + loading/分页状态 | 结果数组、空态、错误态 | 丢弃旧页，不清空新关键词结果 |
| 歌词竞态 | `lyricRequestToken` + `currentLyricSongId` + page visibility | 歌词表、面板显示、失败提示 | 旧歌词不渲染 |
| 缓存未就绪 | `whenReadyOnQueue` ready gate | Loader、缓存列表、迁移 | 延迟准入，不阻塞启动/网络 delegate |
| 缓存清空与迟到写入 | `cacheGeneration` + clear barrier + active write count | `.tmp/.mp3`、L1、账本 | 旧写入失效，新写入延后 |
| 认证失效 | `refreshLockQueue` + pending requests + retry count | 401/301 请求 | 单次刷新、单次重放，或恢复器收到失败/重放再失败时登出；刷新端点自身 301/401 会挂起 |
| 下载迟到回调 | song ID reservation + generation + context identity | 状态、进度、离线正文 | 丢弃旧 task 结果 |
| WCDB 跨表写入 | serial `writerQueue` + WCDB transaction | 关系、实体、下载完成记录 | transaction 回滚，完成回调为失败 |
| 普通缓存与离线资产冲突 | 目录和账本所有权分离 | LRU、删除、播放查找 | 普通缓存不触碰离线正文 |
| 文件与数据库不一致 | fsync、rename 回滚、启动对账、长度检查 | 缓存完成状态 | 候选标记未命中或下次重试 |

这些手段解决的是不同层次的问题：

- **取消**减少无效工作；
- **token/generation**让迟到结果失效；
- **锁/串行队列**保护内存映射和写入顺序；
- **事务**保护同一数据库内的多表状态；
- **对账**修复数据库和文件系统之间无法跨系统原子的窗口；
- **长度/Range 校验**保护结构完整，但不等于内容摘要校验。

## 11. 工程决策与方案取舍

### 11.1 MP3 + HTTP Range + ResourceLoader，而不是直接切 HLS

**问题**：当前上游提供的是可按 HTTP Range 访问的单文件音频。

**选择**：用 `AVAssetResourceLoader` 接管 `streaming://`，自行管理 Range、缓存和离线文件。

**代价**：需要自己处理 Range 缺口、响应校验、文件账本、缓存清理、URL 失效和并发取消；当前没有 HLS 分片、FairPlay 或 DRM。

**什么时候换方案**：如果产品需要自适应码率、商业版权保护、密钥租约、HLS 离线媒体选择或更强的 CDN 调度，应以 HLS/加密资产管理为主，而不是继续扩大单文件 MP3 Loader 的职责。

### 11.2 `AVAssetResourceLoader`，而不是本地 HTTP Proxy

**问题**：需要改变 AVPlayer 的数据来源，又不希望额外启动本地 HTTP 服务。

**选择**：使用 AVFoundation 原生 `AVAssetResourceLoaderDelegate`，请求粒度直接对应 `AVAssetResourceLoadingRequest`。

**代价**：必须严格实现 content information、Range 响应、取消、继续加载和 AVPlayer 的生命周期约束。

**什么时候换方案**：如果未来需要多个客户端共享同一代理、统一支持非 AVFoundation 消费者或调试复杂 HTTP 语义，本地 HTTP Proxy 可能更灵活；当前 App 只有播放器消费，Loader 责任更窄。

### 11.3 background `NSURLSessionDownloadTask`，而不是 `AVAssetDownloadTask`

**问题**：需要下载单个 HTTP(S) 音频文件，并在 App 被挂起或重新启动后恢复任务。

**选择**：稳定 identifier 的 background `NSURLSessionDownloadTask`，`taskDescription` 保存 `songId`，`resumeData` 和进度由 `NLOfflineAudioStore` 保存。

**代价**：应用自己负责任务与歌曲的所有权、系统临时文件导入、离线元数据和 WCDB 完成事务；不能直接获得 AVFoundation HLS asset/DRM 语义。

**什么时候换方案**：如果资源转为 HLS asset，并且需要 media selection、持久化 FairPlay key 或 AVFoundation 离线播放，应评估 `AVAssetDownloadURLSession` / `AVAssetDownloadTask`。

参考：

- [Apple：Downloading files in the background](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background)
- [Apple：AVAssetDownloadURLSession](https://developer.apple.com/documentation/avfoundation/avassetdownloadurlsession)
- [Apple：Discover how to download and play HLS offline](https://developer.apple.com/videos/play/wwdc2020/10655)
- [Apple：FairPlay Streaming](https://developer.apple.com/streaming/fps/)

### 11.4 普通缓存与用户下载分离

**问题**：两者都保存音频，但清理策略和用户预期相反。

**选择**：`NLCacheManager` 管理可淘汰播放缓存，`NLOfflineAudioStore` 管理用户下载资产，`NLDownloadRepository` 管理下载状态和完成歌曲。

**代价**：存在两套文件/状态系统，需要启动迁移旧完成下载，也需要单独处理“一键清空”。

**什么时候换方案**：如果资产规模扩大，应进一步抽象 manifest、分片、加密、校验和授权租约；当前分离已经解决最危险的所有权混淆。

### 11.5 token/generation，而不是只取消网络任务

**问题**：取消不是瞬时的，网络、delegate、文件写入和主线程派发之间都可能有迟到回调；音频会话后台激活也可能晚于停止或重置完成。

**选择**：取消用于减少工作；播放 URL、缓存进度、周期进度、item/player KVO、搜索和下载用 token/generation 判定所属上下文；KVO 额外校验 player/item 身份，结束通知以 item 身份过滤。音频会话使用独立 generation，避免旧激活结果影响新生命周期。

**代价**：每条异步链都必须捕获并检查正确的版本号，代码更显式。

**收益**：不依赖取消时序，快速切歌、搜索、暂停重试和后台恢复都能把旧结果安全地作废。

### 11.6 搜索结果使用字典，而不是立即建立完整模型层

**问题**：搜索四种类型的返回字段不同，当前页面只展示有限字段。

**选择**：Service 统一返回 `NSArray<NSDictionary *>`，由当前页面按搜索类型读取字段；歌曲播放时再转换为 `NLSong`。

**代价**：字段名和类型检查分散在页面，编译期约束较弱。

**什么时候换方案**：当搜索结果被多个页面复用、字段映射稳定、需要复杂空态/图片/分页模型时，应拆分 `NLSongSearchResult`、`NLPlaylistSearchResult` 等模型，避免字典逻辑继续扩散。

### 11.7 当前明确不做的生产级能力

当前实现不应包装成商业音乐 App 的完整方案：

- 没有 DRM、FairPlay 和加密离线正文；
- 没有 HLS 自适应码率和分片 manifest；
- 没有内容 hash 来发现同长度损坏；
- 没有真实 CDN 弱网、断网、重定向和 Range 异常的全量现场证据；
- 没有评论写操作、OAuth、真实账号体系；
- 没有把真机后台系统交付等同于本地 session delegate 单测。

这不是隐藏缺陷，而是当前方案的边界；如果产品目标改变，应先改变资产与授权模型，再继续堆叠局部重试代码。

历史计划记录曾对以下接口做过只读探测。2026-10-11 没有重放，也没有可打开的响应文件：

```text
/search?type=1
/search?type=100
/search?type=1000
/search?type=1006
/search?type=1009
/artists?id=...
/dj/recommend
/dj/hot
/dj/program
```

这一级证据只说明探测时接口返回了可解析结构，不能推出：

- 认证后首页长期稳定；
- 图片 URL 长期有效；
- 真实音频 URL 可持续返回正确 Range；
- AVPlayer 首帧、缓冲和切歌体验满足产品要求；
- 所有页面入口都有稳定 UI 截图。

### 12.3 尚未完成的现场验证

以下内容不能在面试或技术评审中描述成“已验证”：

- 新增搜索、艺人和广播路径的稳定端到端 UI 截图；
- 真实 CDN 音频的首帧时延、Range 命中率、重定向和弱网行为；
- 物理设备的 background `NSURLSession` 交付、系统重唤醒和 resume data 恢复；
- 断网后完整的离线播放人工验收；
- 文件同长度内容损坏的检测；
- 商业级 DRM、版权保护、密钥续期和多设备授权；
- OAuth 或真实账户体系；
- 独立创建 Tab、首页顶部筛选、广告 CTA、音乐库艺人菜单。音乐库自建歌单不在这个缺口里。

### 12.4 推荐的验证顺序

接手后若要继续提高可信度，按风险而不是按页面数量验证：

1. 真机真实 CDN：下载、暂停、恢复、删除、离线播放；
2. 真机后台：挂起、系统终止后 session 事件交付；
3. Range 异常：206/200、错误 Content-Range、短响应、重定向和 URL 过期；
4. 快速交互：连续切歌、搜索关键词快速变化、歌词面板开关、下载重试/取消竞态；
5. 数据恢复：文件删除、数据库损坏、迁移中断、缓存清空与后台写入并发；
6. 最后再做新产品入口和 UI 视觉验收。

开始修改前先确认影响的所有权层：

```text
这是内容入口问题？
  → Service / 页面 / 播放意图

这是当前歌曲一致性问题？
  → playSwitchToken / AVPlayerItem identity

这是播放字节问题？
  → ResourceLoader / Range ledger / cache generation

这是用户资产问题？
  → DownloadManager / OfflineAudioStore / DownloadRepository

这是数据库关系问题？
  → writerQueue / transaction / migration
```

不要通过增加一个重试、一个全局布尔值或一个页面特判来掩盖层级错误。先确定结果属于哪个上下文、文件属于哪个所有者、数据库状态的提交前提是什么，再决定代码放在哪一层。
