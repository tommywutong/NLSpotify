## 一、项目顶层定位（30 秒电梯话术）

NLSpotify 是一款以 Objective-C/UIKit 为主的 iOS 在线音乐 App，对接网易云音乐兼容 API；WCDB 与缓存实现包含 Objective-C++ `.mm` 文件。不要用未经测量的总代码行数、性能数字或远端可用性做面试结论；搜索与广播部分按当前已接通范围表述，不把历史计划当成实现。

**核心抓手三件事：**
1. 基于 `AVAssetResourceLoader` 的流式分片缓存与部分 Range 复用，缓存身份使用 `sha256-` 前缀并保留旧完整缓存按 `songId` 命中。
2. Cookie 401/301 刷新队列与单次请求重放。登录态由 `currentCookie` 非空推导；Keychain 为空时会回退旧 `NSUserDefaults` Cookie，不能说只看 Keychain。
3. ReactiveObjC 信号分发的播放器状态、切歌 Token 一致性控制与歌词请求 token 竞态保护。

**技术栈：** UIKit + Masonry + WCDB + AFNetworking + ReactiveObjC + SDWebImage
**架构：** 单例 + Service 层 + Repository 模式 + MVC + ViewModel

## 二、核心技术亮点（5 个面试可深聊点）

### 🎯 亮点 1：L1 内存、L2 临时磁盘、L3 完整磁盘与 Origin 回源

**位置：** `NLAudioMemoryCache.m` + `NLResourceLoader.m` + `NLCacheManager.mm`

**底层逻辑：** 播放器先查独立离线正文；有 `playURL` 时按 `songId + URL.host + URL.path` 的缓存身份查完整 `.mp3`，没有 `playURL` 时按 `songId` 选取最近访问且文件长度匹配的完整缓存；未命中才获取播放 URL。流式播放把真实 URL 改为 `streaming://`，由 `AVAssetResourceLoaderDelegate` 接收 Range 请求。L1、L2 可满足连续区间；缺口回源，写入 L1/L2 后按完整覆盖晋级 L3。

**3 个深度细节：**

1. **L1 连续区间：** `NLAudioMemoryCache` 以稳定缓存身份 + offset 管理 segment；有稳定 songId 时身份包含 `songId + host/path`，无稳定身份时才回退完整 URL。只返回从请求位置起连续覆盖的字节；部分命中后继续查下层，不会跨空洞拼接。
2. **L2/L3 状态分离：** `.tmp + cachedRangesString` 表示“未完成但部分可读”；无空洞覆盖 `[0,totalLength)` 后，POSIX `rename` 将 `.tmp` 原子晋级为 `.mp3`，不保留重复正文。未完成层合计达到 128 MiB、完整层合计达到 500 MiB 后，才按真实文件 size 把超限层 LRU 裁到 90%。启动做对账与恢复，启动和进后台不触发容量淘汰。
3. **启动异步对账：** 缓存表与目录在 Utility 队列核对；读写、清理和消费者先登记 ready callback，完成后异步继续。切歌 token、Loader 取消和下载 generation 会丢弃等待期间失效的操作，不以等待 barrier 换取启动一致性。
   **完成状态协议：** L2/L3 是同一磁盘缓存的部分与完整状态，不是两份正文。完整命中同时要求完成标记、全覆盖 Range 账本和匹配文件长度；字节已完整但提交失败仍不能宣告成功。保留 rename，失败时恢复内存字段并尽力反向改名，重试与启动对账共用晋级规则；有效完整缓存通过本地文件 URL 播放，绕过 ResourceLoader，但没有据此宣称已测得性能提升。

**面试话术：**
> L1 是热点音频片段，L2 是带 Range 账本的 `.tmp`，L3 是完整 `.mp3`；命中 L3 可以在没有 URL 时直接播放。Loader 对本地缓存之间的空洞按边界回源；文件晋级与账本不构成跨系统事务。真实可播放性和首帧时延需要真机与抓包验证。

### 🎯 亮点 2：Token 自增防过期回调（切歌不串声）

**位置：** `NLPlayerManager.m` 的切歌入口、ResourceLoader 取消及 KVO/进度回调。

**痛点场景：** 连续切歌时，旧歌曲的网络、缓存或计时回调可能晚于新歌曲到达；如果直接更新 UI，就可能出现进度和封面错位。这里描述的是需要防范的竞态，不是本轮复现的具体现象。

**解法：** 切歌、停止和媒体服务重置递增 `playSwitchToken`。播放 URL、缓存进度、周期进度及 item/player KVO 回调核对 token 和对应身份；结束通知核对当前 item。旧 Loader 取消网络任务，已写成功的缓存区间仍可落库。用户意图与引擎状态分离：Ready 不等于 Playing，暂停或中断后的迟到回调不能自行恢复播放。

**面试话术：**
> Token 管住过期回调，取消 Loader 管住旧音频请求，二者不是互相替代；只把已经写到磁盘的 Range 纳入可复用缓存。

### 🎯 亮点 3：Cookie 401/301 串行重试队列

**位置：** `NetWorkManager.m` 与 `NLAuthManager.m`。

**核心设计：**
- **串行队列当锁：** `refreshLockQueue` 串行化 `isRefreshing` 和 pending 队列的读写，不需要额外锁。
- **Pending 队列合并：** refresh 期间到达的失效请求挂入 `pendingRequests`。恢复器收到 refresh failure，或一次重放后再遇 301/401 时，会逐个 fail 并 post `NLForceLogoutNotification`。`/login/refresh` 自身返回 301/401 时不会进入这个 failure 回调。
- **Cookie 而非 OAuth：** Cookie 的目标存储是 Keychain，但 `currentCookie` 在 Keychain 为空或读取失败时回退旧 `NSUserDefaults` 值；迁移写失败仍暂时返回旧值。游客登录仅在响应带非空 Cookie 且 Keychain 写入成功时进入主界面。当前登录页只有游客登录按钮。

**面试话术：**
> 这是 Cookie 会话恢复，不是 OAuth access/refresh-token 实现。401 或业务码 301 会进入串行刷新队列；同一窗口内的请求共用一次刷新，随后每个请求至多重放一次。普通业务请求恢复器能收到 refresh failure，或重放后再遇 301/401 时，Scene 会用 `kCATransitionFade` 切回登录页。但刷新请求自己也走 `NetWorkManager` GET；它自身返回 301/401 时，外层 `isRefreshing` 仍为 YES，这次请求只会被放进 pending 队列并挂起，success/failure 和强制登出都不会执行。这不是当前时序下的调用栈递归，也不能把所有刷新失败都说成可靠收口。

---

### 🎯 亮点 4：离线完整缓存与单一切歌入口

**位置：** `NLPlayerManager.m` 的 `playSongAtIndexIfNeeded:` / `playFullyCachedSongAtPath:`。

**做法：** 各切歌入口统一先查 `songId` 完整缓存，命中时用 file URL 建立 `AVPlayerItem`；未命中才复用播放 URL 或异步获取新 URL。未实现下一首预加载，不能承诺秒切和固定首帧时延。

### 🎯 亮点 5：ReactiveObjC 信号驱动 UI 解耦

**位置：** `NLPlayerManager.m` 的 `playbackStateSignal`、`songSignal`、`progressSignal`、`cacheProgressSignal` 与 `hasPlaylistSignal`。

**亮点与边界：** 小播放器、全屏播放器和 TabBar 订阅播放器信号；播放按钮按公开只读的 `wantsToPlay` 显示，实际状态按 `timeControlStatus` 归约，等待数据复用 Loading。Manager 在后台串行队列配置/激活音频会话；中断仅在 ShouldResume 且用户意图仍允许时恢复，耳机拔出取消意图，媒体服务重置必须用户再次播放才重建并恢复位置。切歌、停止、重置统一清理原 owner 的周期观察、KVO、结束通知、Loader 和 disposable；远程命令注册幂等并由 owner 注销。UI 订阅继续使用 `takeUntil:self.rac_willDeallocSignal`，weakify 只处理引用关系。模拟通知和本地真实播放不等于真机中断、蓝牙及后台物理验收。

**音频生命周期补全：** 回到前台仅按当前引擎与意图补发状态、进度及 Now Playing，不自动开播。seek 成功完成后校验 token 和 player/item 身份，再同步实际位置，暂停拖动也更新系统媒体进度。输出断开时读取旧路由，外部输出丢失或旧路由未知时保守暂停，明确只有内置输出时不主动暂停。普通暂停不主动停用会话，不能宣称因此不会抢占其他 App；Playback 默认非混音也不等于所有其他声音都会停止。系统媒体灵动岛由设备和系统决定，不是三项配置齐全就保证显示。

**面试话术：**
> 播放器把状态和控制职责集中在 `NLPlayerManager`：页面订阅状态，系统锁屏信息和远程命令由播放器统一维护。UI 订阅绑定 `self.rac_willDeallocSignal`，避免反复打开全屏播放器时在单例 Subject 上累积空订阅。切歌时的缓存进度订阅另外由 Manager 保存 disposable 并 dispose。

## 四、加分项（"如果重做我会怎么做"）

主动暴露未完成优化，体现 owner 意识：

1. **架构升级：** MVC + ViewModel → MVVM + Coordinator，用 Router 解耦页面跳转，方便单元测试。
2. **网络层：** AFNetworking → NSURLSession + Codable（如果 Swift 化）；或加 GraphQL 层做请求合并。
3. **本地化播放器：** 评估 `AVQueuePlayer`/`AVPlayerLooper` 是否适合未来预加载；当前实现没有下一首预加载，不能承诺秒切。
4. **后台下载边界：** 已用稳定 identifier 的 background `NSURLSessionDownloadTask`、reservation generation 防止删除后的迟到回调复活任务或离线文件。启动只接管系统 `getAllTasks` 仍返回、且 `taskDescription` 能查到 WCDB 下载项的任务；不用持久化 taskIdentifier 反查，也不会为没有系统任务的数据库记录自动新建下载。暂停 `resumeData` 和 Application Support 离线正文实现恢复路径。不承诺用户 force-quit 后续传或失效 `resumeData` 恢复，真机/CDN 需验证。
5. **HLS / 自适应码率：** 当前是单一 MP3 直链；未来可评估 HLS m3u8 切片与弱网码率策略。
6. **CarPlay：** 现有 `MPRemoteCommandCenter` 已覆盖播放、暂停、上下首和进度拖动；CarPlay UI/模板尚未实现。
7. **缓存、下载与评论验证：** 已覆盖稳定身份、L1/L2/L3 交错读取、Range 响应边界、完整缓存恢复、后台下载导入/删除/恢复闸门、离线优先播放和评论复杂字符折叠。已有记录显示 2026-10-02 完整 `NLSpotifyTests` 为 100/100 通过；内容发现相关历史结果为 103/103 通过。仍需真机/CDN、冷启动后台回调和同长度内容损坏验证。
8. **Swift 化路径：** 先把 ViewModel + Service 层用 Swift 重写（OC ↔ Swift 互操作成熟），保留 .mm 的 WCDB 和 AVPlayer 逻辑用 OC。

## 六、补充亮点（二轮扫描实证后修正）

> 以下三条经过源码实证，与初版推测有出入，已按实际代码修正。

### 🎯 亮点 6：歌词同步（响应式信号 + Token 防污染）

**位置：** `NLMusicPlayerViewController.m` 的进度订阅、切歌后的自动歌词请求和 LRC 解析；具体行号随持续开发变化，以方法名和源码为准。

**实际实现：**
1. **LRC 解析**：`NSRegularExpression` 匹配 `\[(\d{2}):(\d{2})\.(\d{2,3})\]` 时间戳，`NLLyricLine` 数组存储，支持同一行多个时间标签并排序。
2. **当前行计算**：线性扫描带起点优化——正常播放从 `currentLyricIndex` 接续，快退时从头搜索。
3. **响应式驱动**：每次 `progressSignal` 事件会在主线程调用 `updateLyricForCurrentTime:`；发射频率由播放器决定，不把它描述成“每帧”。
4. **切歌防污染的范围**：手动点封面且当前没有歌词行才会首次请求；切歌只有 `lyricVisible` 为 YES 才自动请求。两类请求的回调都校验 `lyricPageVisible`、song ID 和 token。收起面板、切歌、离开播放页或新请求都会让旧回调失效，过期 success/failure 不更新歌词、不开面板、不弹失败提示。
5. **UI 居中**：当前行变化时整表 `reloadData`，再用 `scrollToRowAtIndexPath:atScrollPosition:UITableViewScrollPositionMiddle` 居中。

**面试话术（修正版）：**
> 歌词同步是“响应式进度事件 + 增量行索引”。顺序播放从上一个高亮行继续搜索，快退才从头扫描；所有歌词请求都带 song ID + token 校验。它仍是行级歌词，不是逐字时间轴。

**已知短板（被追问要主动承认）：**
- **没有二分查找**：长歌词和快退仍可能为 O(n)。
- **整表 reload**：当前行变化会重载整张歌词表。
- **格式边界**：不支持无小数标签、翻译/逐字歌词（竞态边界已由 song ID + token 校验覆盖）。

### 亮点 7：评论区文本折叠（异步排版与双态文本高度缓存）

**位置：** `NLCommentTextFolder`、`NLCommentTextLayout`、`NLCommentLayoutCoordinator`、`NLCommentCell` 和 `NLCommentListViewController`。

**实际实现：**
1. TextKit 按实际正文宽度逐行计数，在组合字符边界查找带展开尾部的三行前缀；最终富文本使用匹配 UILabel 的字符串绘制度量计算文本高度。
2. 页面协调器最多并发 2 个任务，合并相同布局键；不可变结果缓存折叠/展开富文本及对应文本高度。NSCache 有数量和估算 cost 限制，但页面仍持有当前已加载评论的有效结果，不宣称整个列表内存严格受限或全局 LRU。
3. 主线程捕获内容、宽度和字体环境，结果返回时验证页面代次、模型身份和内容；环境变化或页面离开使旧工作失效。Cell 只应用结果，不在 `layoutSubviews` 中重排。
4. 新页准备后增量插入；普通展开/收起无动画批量更新行高，由 UITableView 负责滚动位置协调，不再额外恢复整表锚点。分页与整体环境重排才走现有阅读锚点路径。缓存的是正文高度，整行由 Auto Layout 计算，不再从 Model 读取旧整行高度。
5. 短评论不切换状态，长评论保留整段点击，并提供 VoiceOver 展开/收起操作；复用清理状态和旧头像任务。

**简历表述：**
> 基于 TextKit 实现评论三行折叠与展开收起，通过有界后台排版、双态富文本及文本高度缓存降低主线程排版负担；结合布局环境失效、过期结果校验、分页增量更新及整体重排时的阅读位置维护，提升列表更新的一致性。

### 🟠 面试常被追问的"反直觉"问题

1. **"为什么用单例不用依赖注入？"**
   答：单例是为快速迭代，下版本会用 Resolver / Swinject 模式注入，便于测试 mock。

2. **"AVAssetResourceLoader 为什么不用 AVAssetDownloadURLSession？"**
   答：项目当前是单文件音频，显式下载使用后台 `NSURLSessionDownloadTask`；`AVAssetDownloadURLSession`/`AVAssetDownloadTask` 的媒体资产语义不能直接替代任意 MP3 单文件下载。未来引入 HLS 或 DRM 时再单独评估，当前优先保证暂停、恢复、删除和离线正文所有权可控。

3. **"为什么不用 OAuth2 标准库？"**
   答：当前实现走 Cookie 会话恢复，不是 Bearer Token/OAuth2 授权流；引入 OAuth2 库无法替代现有协议，需要由服务端接口能力决定。
4. **"为什么不用 GCDWebServer 做本地代理？"**
   答：GCDWebServer 启 HTTP server 占端口，AVPlayer 通过 localhost 访问，在后台模式下易被 iOS 杀掉；ResourceLoader 走 Delegate 回调，在 process 内闭环更稳。

5. **"WCDB 相比 Core Data / FMDB 的优势？"**
   答：当前项目使用 WCDB 的 Objective-C ORM 绑定和事务 API 管理本地歌曲、歌单与缓存账本；Core Data 擅长对象图、faulting 等场景，但本项目现有表结构没有据此迁移的需求。不在缺少同条件基准测试时声称性能优于 Core Data，也不把库的可选加密能力说成当前项目已启用。
   存储位置上，数据库属于应用内部持久数据，放在 `Library/Application Support/NLSpotify/`，不放用户文档目录。升级时使用 WCDB 的 `moveFilesToDirectory:` 搬迁旧 Documents 数据库及伴随文件，避免仅移动主库丢失 WAL 数据；新位置已有数据库时不覆盖。

## 八、面试 STAR 答题模板（可直接背诵）

> STAR = Situation 情境 / Task 任务 / Action 行动 / Result 结果
> 每条 90 秒以内讲完，不要超时。

---

### STAR 1：流式分片缓存（最强抓手，必背）

**S 情境：**
> 仿 Spotify 的项目里，用户痛点是同一首歌反复加载浪费流量、弱网下首帧延迟高；同时拖动进度会产生非连续 Range 请求。

**T 任务：**
> 在不引入第三方播放库的前提下，做边播边缓存与完整文件复用：当前进程内热点走内存，未完成字节可断点复用，完整文件可在冷启动后本地播放；网络只补缺口。

**A 行动：**
> 顶层设计上我用 `AVAssetResourceLoaderDelegate` 拦截 `streaming://` 的 Range 请求，形成四段路径：
> 1. **L1 热点内存：** `NLAudioMemoryCache` 以稳定缓存身份 + offset 保存连续 segment。播放器传入的稳定身份是 `songId + host + path`，不包含 query；接口注释写 query tokens are ignored，但源码没有证明 query 是签名参数。没有稳定身份时才散列完整 URL，那时 query 会参与身份。`NSCache` 成本上限 12 MiB、数量上限 512；
> 2. **L2 部分磁盘：** `.tmp + cachedRangesString` 描述已写入区间，`pread` 命中后回填 L1，Origin 只请求空洞；
> 3. **L3 完整磁盘：** 无空洞覆盖整首后，用同目录 `rename` 把 `.tmp` 原子晋级为 `.mp3`，不保留重复正文。L2 高水位 128 MiB、L3 高水位 500 MiB，写入后只裁超限层到 90%；启动和进后台不触发。无 URL 时按 `songId` 选最近访问且文件长度匹配的完整行，不把 `sha256(songId)` 当文件名；
> 4. **并发与账本：** 标识分片写入按 identifier 哈希分配到 8 条串行队列；准入另有 admission queue。网络数据同时交播放器、写入 L1/L2。缓存账本由缓存队列直接写 WCDB，不经过 Repository writer queue。

> 已记录的 2026-10-02 历史测试覆盖 Range 校验、L1 segment、L2/L3 读写、清理、稳定身份、无 URL 本地命中、rename 窗口恢复及负例、后台缓存列表和取消路径；记录还包含缓存 `sha256` 身份、旧 schema 启动迁移（RED→GREEN）与旧完整缓存按 `songId` 命中测试，完整 `NLSpotifyTests` 为 100/100 通过。模拟器仅验证未登录根页面启动；真实 Origin/CDN、首帧时延、命中率和物理设备播放仍需单独验证。

### STAR 2：Cookie 401/301 串行重试队列

**S 情境：**
> 网易云兼容接口依赖 Cookie；HTTP 401 或业务码 301 表示当前请求需要进行会话恢复。

**T 任务：**
> 避免同一失效窗口内的多个请求各自触发刷新，并限制请求重复次数。

**A 行动：**
> 1. `refreshLockQueue` 串行化 `isRefreshing` 和 `pendingRequests`；
> 2. refresh 期间到达的请求入队；
> 3. 刷新成功后复制队列、清空原队列并让每个请求至多重放一次；
> 4. 普通业务请求恢复器收到刷新失败，或一次重放后再遇 301/401 时，清理本地登录态、post `NLForceLogoutNotification`，由 Scene 用 `kCATransitionFade` 切回登录页。`/login/refresh` 自身 301/401 会在 `isRefreshing == YES` 时入队挂起，不调用 refresh failure，也不能把这条收口外推为所有刷新失败都可靠登出。

**R 结果：**
> 源码具备并发失效请求共享一次 Cookie 刷新的控制流。目标存储是 Keychain，但 `currentCookie` 在 Keychain 为空或读取失败时仍回退旧 `NSUserDefaults` 值；历史测试覆盖迁移成功、写失败保留旧值，尚无针对真实服务端并发 401 的执行证据，不将假设的请求数量或“彻底闭环”作为实测结果。


---

### STAR 3：Token 自增防过期回调

**S 情境：**
> 连续切歌会让播放 URL、缓存和计时回调晚于新歌曲到达；如果旧结果直接更新页面，当前歌曲与进度可能错位。这里描述的是需要防范的竞态，不是本轮复现的具体现象。

**T 任务：**
> 让旧请求的结果不污染当前播放，同时取消旧 Loader；已成功写入的缓存 Range 仍可在取消后的合并路径中保存。

**A 行动：**
> `NLPlayerManager` 切歌时递增 `playSwitchToken` 并捕获当前 token；异步返回时校验 token 与当前歌曲，过期直接丢弃。例如源码中的播放 URL 回调：
> ```objc
> __strong typeof(weakSelf) strongSelf = weakSelf;
> if (!strongSelf || token != strongSelf.playSwitchToken || strongSelf.currentSong != song) return;
> song.playURL = playURL;
> [strongSelf playWithURL:playURL];
> ```
> 计时回调还校验当前 `AVPlayerItem`；切歌时取消旧 Loader，成功写入的 `sessionRanges` 会在写入组完成后合并到账本。

**R 结果：**
> Token、取消与 Range 合并是互补关系：Token 防止旧状态更新当前 UI，取消停止旧资源请求，已确认写入的区间保持可复用。当前没有把这个结论外推为真实网络下的首帧或缓存命中率指标。

---

### STAR 4：完整缓存命中与单一切歌入口

**S 情境：**
> 播放 URL 可能过期，但完整缓存的歌曲应该仍能在本地播放。

**T 任务：**
> 让列表切歌、直接选曲和播放 URL 回调走同一入口，并优先复用完整缓存。

**A 行动：**
> `playSongAtIndexIfNeeded:` 递增 token、清理旧播放器资源并先按 `songId` 查完整缓存；命中后以 file URL 创建 `AVPlayerItem`，未命中才复用 `playURL` 或异步请求新 URL。

**R 结果：**
> 单测覆盖无播放 URL 的完整缓存命中。当前没有下一首预加载、双 `AVPlayerItem` 或首帧时延测量，不能描述成“秒切”。

---

### STAR 5：评论区文本折叠（TextKit + 双态缓存）

**S 情境：**
> 评论正文需要在不展开完整文本的情况下保持列表信息密度。

**T 任务：**
> 对超过三行的正文提供展开/收起，在后台准备可复用的文本与高度，并使分页、字号变化和重复展开后的列表位置保持一致。

**A 行动：**
> 1. 用 TextKit 在组合字符边界计算三行折叠文本，并测量匹配 UILabel 的最终文本高度；
> 2. 有界异步任务合并同键请求，缓存不可变双态结果，以页面代次、内容和布局环境丢弃旧结果；
> 3. Cell 应用缓存正文高度、Auto Layout 计算整行；普通展开让系统协调滚动偏移，避免二次补偿；分页增量插入，整体重排按需恢复阅读位置，并提供辅助操作。

**R 结果：**
> 已有真实 Cell/列表、异步竞态和动态布局回归，以及实际 App 的本地 smoke 与模拟器滚动采样。可以说明布局计算移出主线程、缓存命中不重复排版，但没有改造前后 Instruments/FPS 对比，不宣称性能提升百分比；评论功能仍为只读。

**当前实现：**

### 首页并发装配：固定槽位 + `dispatch_group`

**当前实现：**
> `NLHomeViewModel` 并发请求五个推荐分区：个性化推荐、歌手专辑和华语/欧美/流行歌单。先用五个 `NSNull` 固定槽位，再由每个请求写回自己的下标；success 和 failure 都执行 `dispatch_group_leave`，`notify` 回到主队列后过滤失败槽位、复制成不可变快照并回调控制器刷新。
